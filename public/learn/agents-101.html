Section 01

What makes an AI an agent

Most AI tools are mail slots. You push a question in, you get an answer back, it's done. An agent is something different. It's closer to a smart friend who can actually get up, open drawers, make calls, check things, and come back when the task is finished.

📬

Plain chat = a mail slot

You put a letter in. One answer comes back. That's it. ChatGPT without tools is mostly this. It cannot DO anything. It can only DESCRIBE doing things.

🤝

Agent = a smart friend with real access

You say "book me a flight under $400." They open their laptop, search three sites, compare prices, pick one, run your card, and text you the confirmation. They didn't just TELL you what to do. They did it.

The trick that makes this work is a loop. Four steps that repeat until the job is done.

Each time around the loop the model figures out what tool to use next, runs it, reads what came back, and decides whether to keep going. When it's finally done it stops and reports back.

The four-part formula

Agent = model + tools + that loop + memory of what it's doing. Take away any one of these and you don't have a real agent. A model alone is just a chat. Tools without a loop is just one function call. Memory is what lets it stay on task across many steps.

The "tools" can be anything. Reading a file. Searching the web. Writing code. Calling an API. Sending a Slack message. The model doesn't DO those things directly. It decides what to call. The engine runs the call. The result comes back. The model thinks about it. Repeat.

A friend says "Claude just chatted with me and told me what to research." Is that an agent? Check yourself ▼
Good answer:

No. That's plain chat: one question, one answer, done. An agent would have DONE the research itself. It would have used a search tool, read the pages, synthesized the results, and handed you the finished work. If Claude only DESCRIBED what to do instead of doing it, it was working as a mail slot, not an agent.

You can now explain: The difference between a chat model and an agent is the loop. An agent uses tools, sees what happens, and keeps going until the task is actually done.
Section 02

The Claude Agent SDK

Think of it as "Claude Code in a box you can build with." It gives you the same brain, tools, and rules that power the Claude Code app, but as a library you import into your own software.

Before the Agent SDK existed, if you wanted an agent, you had to build the loop yourself. That meant:

The old way (hard)

Parse the tool call that came back from the model. Run it yourself. Feed the result back in. Watch for infinite loops. Handle streaming. Manage conversation history. Wire up permissions. Do this forever, for every project, from scratch.

The Agent SDK does all of that for you. You call one function:

import { query } from '@anthropic-ai/claude-agent-sdk' const result = await query({ prompt: 'Find all my overdue tasks and summarize them', options: { maxRounds: 10 } }) // The loop, the tool calls, the results — all handled. // You get back the finished answer.

And what comes with that one call:

Files + Terminal

Read, write, and run shell commands. Same tools Claude Code uses day-to-day.

Your MCP servers

Notion, Gmail, Spotify, Supabase, anything you've wired into Claude Code comes along for free.

Skills + CLAUDE.md

Your existing skills and memory files are automatically in scope. The agent knows your setup.

Session memory

You can give an agent a session ID so it can resume across interruptions, like a thread it can pick back up.

Permission controls

Decide which tools the agent can use. You don't have to let it touch everything.

Streaming output

Words and tool events flow back in real time. You see what it's doing as it happens.

The key distinction

@anthropic-ai/sdk (plain SDK) = one model call. You write everything around it, the loop, the tools, the memory, the permissions. All on you.

@anthropic-ai/claude-agent-sdk (Agent SDK) = the loop, tools, memory, and permissions built in. You just describe what you want done.

What the Agent SDK is NOT: it is not a no-code tool. It is not a visual workflow builder. It is not a finished product you just click through. It is a library for people who write code and want an agent that runs inside their own software, with their own rules.

You can now explain: The Agent SDK is Claude Code turned into a library. It gives you the loop, the tools, and the memory management so you don't have to build those yourself every time.
Section 03

The four layers people mush together

Everyone in AI throws around the same words: frameworks, engines, models, conventions. They are not the same thing. Here's a map. Click any layer to see what it actually means and where Kitsu fits in it.

🧠
Model
Raw brain
▼

The model is just the brain. It reads text and predicts what should come next, at a staggering level of quality. That's all it does.

It has no memory between conversations by itself. It cannot run code or search the web on its own. It can DESCRIBE doing things but not actually do them. That's why all the other layers exist.

Where Kitsu sits: Kitsu uses Claude (Sonnet 4.6) as the model. Kitsu is NOT the model. The model is one piece.

Claude (Anthropic) GPT-4o (OpenAI) Gemini (Google) Llama (Meta)
⚙️
Engine / Runtime
Powers the loop
▼

The engine wraps the model into an actual agent. It runs the loop (think, use tool, observe, repeat), manages tools, handles streaming, enforces permissions, and tracks session memory.

Without an engine you are manually managing all of that in code every time. With an engine you call one function and describe what you want.

Kitsu runs on this layer. The Claude Agent SDK IS the engine. This is why Kitsu does not need a framework: the engine already provides the loop and tools.

Claude Agent SDK Claude Code (app)
📄
Convention
Shared file shape
▼

A convention is not software. It is an agreed-upon way of organizing files so any agent on any engine can read them and know what to do.

The most common example is soul.md files, popularized by the OpenClaw project. The files are just markdown. The "convention" is what goes in each one: identity, memory, user profile, core values. Any engine that reads these files gets the same grounded agent.

Kitsu is adopting this convention right now. We borrow the FILE SHAPE from OpenClaw. We do NOT use the OpenClaw framework itself.

soul.md files AGENTS.md CLAUDE.md
🏗
Framework
Opinionated toolkit
▼

A framework is an opinionated toolkit that sits on top of a model and engine and helps you wire up complex multi-agent systems, scheduling, UI, and memory patterns. They make common agent patterns fast to set up.

The tradeoff: frameworks give you speed for their patterns, but they also lock you into their opinions. You trade control for convenience.

Kitsu does NOT use a framework. The Claude Agent SDK already provides the loop and tools. Adding a framework on top would add abstraction without adding capability for what we are building.

OpenClaw LangGraph CrewAI Mastra n8n
📦
Product
Finished agent
▼

A product is a finished agent that an end user just opens and uses. The loop, the tools, the memory, the engine, all of it is hidden. You don't configure it. You just talk to it.

Claude Code is a product. Cursor is a product. Manus and Devin are products. You use them without knowing which engine they run on.

Kitsu lives between PRODUCT and ENGINE. It has a face (the PG OS app), which is product-like. But the soul and config are fully yours to shape. That's unusual. Most products don't let you into the engine room.

Claude Code (app) Cursor Manus Devin Kitsu (partly)
Someone says "I'm using LangGraph as my model." What layer did they get confused? Check yourself ▼
Good answer:

They confused FRAMEWORK with MODEL. LangGraph is a framework (an opinionated toolkit for wiring agents together). The model is the raw brain, like Claude or GPT. LangGraph uses a model; it is not a model. Same mistake people make when they say "I'm using CrewAI" without specifying which model it's running on top of.

You can now explain: There are five layers in the agent stack. Model is the raw brain. Engine runs the loop. Convention is a file shape. Framework is opinionated tooling on top. Product is the finished thing users open.
Section 04

SDK vs frameworks: the practical difference

This is the comparison that comes up constantly. Once you can hold this clearly, you can explain any new tool you encounter in about ten seconds.

Claude Agent SDK

This is the ENGINE layer. It gives you maximum control because it hands you your actual Claude Code runtime: your real MCPs (Notion, Gmail, Spotify), your real CLAUDE.md and skills, your real permission model. Nothing is abstracted away. You are running the same brain that runs Claude Code, in your own code. No framework needed on top.

OpenClaw / "system claw"

OpenClaw is a FRAMEWORK plus the soul.md CONVENTION. Out of the box it gives you a fast personal assistant. The tradeoff is that you are inside their opinions: their routing, their memory management, their tool patterns. It's a good starting point for a personal assistant that doesn't need to be deeply customized.

We borrow OpenClaw's soul.md FILE SHAPE because it is a good convention. We do not use the OpenClaw framework itself, because the Agent SDK already gives us a better engine for Kitsu's use case.

Mastra / LangGraph / CrewAI / AGENTS.md

These are other frameworks and conventions. They each have a niche. LangGraph is great for complex multi-agent state machines. CrewAI is fast for role-based multi-agent systems. Mastra is designed for TypeScript-first agent apps. AGENTS.md is a convention (like soul.md) for grounding an agent's identity in a file.

None of them hand you your literal Claude Code runtime the way the Agent SDK does. That's the key thing the Agent SDK has that nothing else has.

The mental model for picking between them:

🏠

Framework = furnished apartment

Move in fast. Furniture is already there. You can rearrange a bit, but the floor plan is theirs.

🧱

Agent SDK = raw building materials

You build the floor plan yourself. More work upfront. Everything is exactly where you want it. Nothing you didn't put there.

You can now explain: The Agent SDK gives you your real Claude Code runtime, which no framework can match. Frameworks are faster to start but less control. We use the SDK and borrow soul.md files from OpenClaw's convention.

Section 06

Soul files, memory, and persona drift

Every agent wakes up fresh. No memory between sessions. If you don't give it something to read, it starts from zero every time. That's the problem soul files solve.

😴

Agents are amnesiac by default

Each new conversation is a blank slate. The model has no idea who you are, what you've built together, or how you like to work. It's like hiring the same contractor every morning who forgot everything from yesterday.

The fix is simple: write what the agent needs to know into files, and have him read them at the start of every session. That's the soul.md pattern in one sentence.

The soul.md pattern

You write a set of markdown files with the agent's identity, your user profile, and distilled memory. The agent reads these files at the top of every session before doing anything else. Now he "remembers" who he is and who you are, every single time.

Here's what the four core soul files hold:

IDENTITY.md
Who Kitsu is. His name, his role, his core purpose. The anchor that keeps him from becoming generic over time.
SOUL.md
His values and personality. How he communicates. What he cares about. This is what makes him YOURS and not a clone of every other assistant.
USER.md
Who you are. Your projects, your goals, your preferences, your context. So he doesn't ask "wait, what's Kitsu again?" every session.
MEMORY.md
Distilled lessons from past sessions. Corrections you gave him. Decisions you made together. The living record of how your working relationship has evolved.

Now here's a subtler problem: persona drift.

Persona drift (the Anthropic research finding)

Anthropic researchers found that even within a single long conversation, an agent's personality can drift away from its intended identity. The model adapts to whatever tone and style the conversation develops, and over many turns, the original persona gets blurred.

The fix: a SHARP soul. Not a wall of text. The soul files need to be tight, specific, and memorable enough that they pull the agent back to center every session. Too long, and the model treats them like fine print. Short and sharp, and they actually stick.

This is why there is a "distill" step in Kitsu's memory cycle. The raw correction log grows over time. Periodically, that log gets summarized down into the soul files. The soul stays short and sharp. The log holds the full history for reference. The agent reads the soul, not the log.

🍵

Soul = a strong tea, not a bucket of water

A concentrated soul file flavors the whole session. A sprawling wall of text gets skimmed and forgotten. Keep it sharp. Let the distill pass do the compression.

Kitsu gave you a weird formal answer that sounded nothing like him. What probably happened, and what's the fix? Check yourself ▼
Good answer:

Persona drift. Over a long conversation, Kitsu adapted to a more formal tone (maybe you wrote something formal, or the conversation went down a technical rabbit hole). The fix: run a distill pass on the soul files to make his identity sharper. Also consider shorter sessions that re-read the soul at the start. The soul being SHORT AND SPECIFIC is the best ongoing defense.

You can now explain: Soul files solve the amnesia problem by giving the agent something to read every session. Keeping the soul SHORT and SHARP fights persona drift. The distill step compresses the log back into the soul so it stays readable.
